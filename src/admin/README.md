# Админка

Панель управления сайтом: заявки, цены, контакты. Работает только
локально и на сервере с Node — на виртуальном хостинге её нет вовсе.

## Как запустить

```bash
npm run dev
```

Открыть `http://localhost:3001/admin`.

Перед первым запуском нужны две вещи.

**Ключ подписи** — в `.env.local`:

```bash
node -e "console.log('ADMIN_SECRET='+require('crypto').randomBytes(32).toString('base64'))" > .env.local
```

Без него админка не запустится и скажет об этом. Запасного ключа в коде
нет намеренно: ключ из репозитория известен всем, у кого есть
репозиторий.

**Пользователь** — отдельной командой (сервер разработки при этом должен
быть остановлен, см. ниже):

```bash
npm run admin:user -- vladelec
```

Команда создаёт владельца и печатает пароль один раз. В базе лежит
только хеш. Повторный запуск с тем же логином меняет пароль.

## Почему её не видно на боевом сайте

Страницы админки называются `page.admin.tsx`. Это расширение разрешено в
`next.config.ts` только в серверном режиме; при сборке статической
выгрузки (`npm run build:static`) его в `pageExtensions` нет, и Next
этих файлов не видит. В выгрузке админки не существует — не «есть, но
не работает».

Это важно: она пишет в базу и принимает пароль, а выгрузка уезжает на
публичный хостинг reg.ru.

## Как устроены правки

Каталог приходит из выгрузки поставщика, и при обновлении прайса
таблица товаров перезаписывается целиком. Поэтому правки владельца
лежат **отдельной таблицей** `overrides` и накладываются поверх при
чтении. Импорт их не видит.

Путь правки до сайта разный для товаров и для остального:

| | Товары | Контакты, цены установки, электрика |
|---|---|---|
| Где читается | прямо в запросе, `src/catalog/overrides.ts` | из файла `data/content-overrides.json` |
| Кто кладёт | — | `npm run apply-overrides` перед сборкой |
| Почему так | страницы товаров и так читают базу | телефон стоит на 8 251 странице, и они синхронные |

Правка ложится с `published: false` и копится в очереди: витрина — это
статические файлы, пересобирать их на каждое нажатие бессмысленно.
Счётчик «N правок не на сайте» виден в меню из любого раздела.

## Списки владельца

Отзывы, акции, снимки работ и добавленные вопросы — не правки, а свои
записи, поэтому у них свои таблицы (`reviews`, `promos`, `works`,
`faq`), а не слой `overrides`.
Работает это так:

- **Добавить** создаёт пустую скрытую запись, поля заполняются по
  одному и сохраняются сами. Форма «заполни и нажми» теряла бы
  набранное при закрытой вкладке.
- **Показывать на сайте** — флажок `visible` у записи. Не путать с
  публикацией: запись может быть видимой, но ещё не уехавшей на сайт.
- **Выкладка** отсеивает незаполненное: отзыв без текста, акция без
  заголовка, снимок без файла до витрины не доходят.
- Любая правка списка ставит метку `__dirty` в `overrides` — иначе
  добавленный отзыв не попал бы в очередь публикации.

Галерея показывает сначала девятнадцать снимков из кода
(`src/content/works.ts` — подписи сверены по шильдикам), потом
добавленные владельцем.

Вопросы устроены так же, но с добавкой: десять прежних лежат в коде и
правятся **слоем**, а не переписываются. Их тексты связаны с другими
страницами — сроки в ответе про установку обязаны совпадать с таблицей
сроков, — поэтому исходный текст остаётся виден, и видно, от чего
владелец отклонился. Ненужный вопрос снимается с витрины
переключателем: удалённый пришлось бы набирать заново.

Вопросы делятся на два списка полем `scope`: `home` — главная и
страница установки, `catalog` — страница каталога. Человек в каталоге
ещё выбирает деталь, и гарантия на работы ему в этот момент не нужна.

## Картинки

Загруженное кладётся в `public/images/own/` — отдельно от
`public/images/products/`, куда пишет парсер заводов: иначе следующий
запуск парсера затёр бы фотографию владельца.

Файл всегда пересохраняется через sharp:

- разворачивается по EXIF и ужимается до 1600 пикселей (снимок с
  телефона на 4 МБ становится файлом на 200 КБ);
- метаданные не переносятся — в EXIF лежат координаты съёмки, и
  фотография, сделанная дома, выдала бы адрес владельца;
- «картинка», которая на самом деле не картинка, до папки не доходит:
  sharp падает на разборе.

Куда прикрепляется:

| Где | Как хранится |
|---|---|
| Снимок работы | поле `photo` записи в таблице `works` |
| Фотография товара | правка `photo` в `overrides` — иначе выгрузка поставщика затёрла бы её |

Всё из `public` попадает в статическую выгрузку как есть, поэтому
загруженное уезжает на сайт вместе со следующей сборкой.

## Публикация

```bash
npm run publish -- --dry           посмотреть, что изменилось
npm run publish -- --to ../proba   залить в папку рядом (проверка)
npm run publish                    залить на хостинг
```

Пересборка полная — `output: 'export'` у Next частичной не умеет, и
обещать минуту вместо двадцати было бы враньём. **Заливка выборочная:**
скрипт считает отпечатки всех 54 тысяч файлов (около минуты),
сравнивает с прошлой выкладкой и отправляет одним архивом только
разницу. Правка одной цены меняет десяток файлов, а не 1,3 ГБ.

Куда заливать — через окружение:

```bash
PUBLISH_SSH=u3637241@server106.hosting.reg.ru
PUBLISH_PATH=~/vashfarkop.ru/public_html
```

Отметка «опубликовано» ставится последней, после подтверждённой
заливки: пометь раньше и упади заливка — правки исчезнут из очереди, а
на сайте их не будет.

**Один раз,** раз сайт уже выложен руками:

```bash
npm run publish -- --skip-build --assume-published
```

Это записывает нынешнюю папку `out` как состояние сервера. Без него
первая публикация сочла бы изменившимися все файлы.

## Чего ещё нет

- **Кнопки «Опубликовать» в самой админке.** Скрипт готов и проверен,
  но запускать его должен сервер с Node — на нынешнем хостинге его
  нет.
- **Приёма заявок с сайта.** Таблица `requests` готова и экран заявок
  работает, но формы на статической витрине писать в неё некуда — там
  нет сервера. Включится вместе с переездом.

## Грабли

**Базу держит один процесс.** PGlite однопоточный: пока запущен
`npm run dev`, любой скрипт, открывший `.pgdata`, работает со своей
копией данных. Записи не дойдут до сервера, а сервер продолжит
показывать своё — молча, без ошибки. Перед `npm run migrate`,
`admin:user` и `apply-overrides` сервер надо останавливать.

**Резкая остановка сервера может сделать базу нечитаемой.** PGlite — это
PostgreSQL в WebAssembly, и восстановление после недописанной записи он
не тянет: при следующем открытии падает с `RuntimeError: Aborted()` без
внятного сообщения. Чинится полной пересборкой, это минута:

```bash
mv .pgdata .pgdata.broken     # на всякий случай, потом удалить
npm run restore-data          # развернёт каталог заново из дампа
npm run admin:user -- vladelec
```

Бояться тут нечего: `.pgdata` — расходный материал. Каталог целиком
лежит в `data/catalog.json.gz`, опубликованные правки — в
`data/content-overrides.json`. Теряются только пользователь админки,
непубликованные правки и заявки. Когда появятся заявки, базу надо будет
регулярно выгружать — это отдельная задача для сервера.

## Файлы

| | |
|---|---|
| `session.ts` | подписанная печенька на HMAC, без внешних пакетов |
| `password.ts` | scrypt из `node:crypto` |
| `throttle.ts` | пять неудачных попыток входа — пауза пять минут |
| `auth.ts` | `requireAdmin()` — вызывается в каждом действии и на каждой странице |
| `actions.ts` | серверные действия: вход, правки, заявки |
| `store.ts` | запись правок и очередь публикации |
| `content.ts` | чтение правок для показа в самой админке |
| `products.ts` | список товаров с обеими ценами |
| `lists.ts` | отзывы, акции, снимки: добавить, править, передвинуть |
| `uploads.ts` | приём картинок: проверка, разворот по EXIF, сжатие |
| `nav.ts` | разделы меню |
| `when.ts` | даты словами, по московскому времени |

Скрипты: `scripts/publish.mjs` (сборка и выборочная заливка),
`scripts/apply-overrides.ts` (выкладка правок в файлы для сайта),
`scripts/admin-user.ts` (завести владельца), `scripts/migrate.ts`.
